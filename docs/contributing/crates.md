# Rust crates

Janiform's Rust code lives under `crates/` as one Cargo workspace. Crates are ownership boundaries, not just folders. Add or move code based on the domain that owns the behavior and the direction of dependencies in the workspace.

For Rust style rules inside a crate, see [Rust conventions](rust-conventions.md). For generated crate README and crate graph artifacts, see [Generation scripts](generation-scripts.md).

## Workspace shape

The workspace is declared in the repository root `Cargo.toml`. Each crate has its own `Cargo.toml`, generated `README.md`, and `src/` tree.

The main crate kinds are:

- production crates for model, market-time, engine, calibration, validation, verification, governance, event-log, terminal UI, and workflow behavior
- boundary crates for command-line and Python integration
- the `janiform` facade crate, which curates Rust-facing module roots
- test-only and benchmark-only crates for shared test support and benchmark governance

The crate graph policy fixture at `tests/fixtures/rust_architecture/internal_crate_graph_policy.json` records crate classification, layer, and allowed internal dependencies. It is generated by `scripts/generate_internal_crate_graph_policy.py`.

When editing a crate's `Cargo.toml`, check whether any dependency points at another workspace crate. Adding, removing, or moving one of those internal dependencies changes the approved crate graph, so regenerate the policy fixture with `python scripts/generate_internal_crate_graph_policy.py` before running Rust tests.

## Choosing the owner

Put new Rust behavior in the crate that owns the domain:

| Crate or crate family | Owns |
| --- | --- |
| `janiform-foundations` | Foundational contracts and small shared primitives. |
| `janiform-model-kernels` | Stochastic model kernels. |
| `janiform-engine-*` | Pricing, simulation, and sufficient-statistics execution. Sufficient statistics are compact path summaries used by downstream engines instead of replaying every simulated tick. |
| `janiform-market-time` | Reusable market calendar and market-time behavior. |
| `janiform-calibration-artifacts` | Calibration artifacts and serialized calibration contracts. |
| `janiform-calibration-runtime` | Calibration execution. |
| `janiform-validation` | Model validation. |
| `janiform-verification` | Verification harnesses and cross-engine checks. |
| `janiform-governance` and `janiform-governance-bench` | Performance baselines, benchmark policies, benchmark execution support, and drift reports used to decide whether model/runtime behavior has changed acceptably. |
| `janiform-workflows` | Workflow orchestration for fitting, simulation, pricing, validation, generated artifacts, and shared progress/event reporting. |
| `janiform-cli` | Command parsing and terminal command behavior. |
| `janiform-pybind` | Python bindings. |

If the behavior is useful to more than one downstream crate, move it to the lowest appropriate shared crate instead of adding duplicate helpers.

## Dependency direction

Dependencies should point from higher-level orchestration and boundary crates toward lower-level domain crates.

Avoid reversing that direction. Core model, engine, validation, and calibration crates should not depend on CLI, PyO3, terminal rendering, or workflow shell concerns.

The boundary and orchestration crates are intentionally near the edge of the graph:

| Crate | Role |
| --- | --- |
| `janiform-cli` | Owns CLI parsing, command dispatch, shell output, and command-line diagnostics. |
| `janiform-pybind` | Owns the PyO3 boundary and converts Python values into Rust contracts as early as possible. |
| `janiform-workflows` | Owns shared workflow orchestration used by boundaries. |

The `janiform` crate is the umbrella facade. It should expose curated Rust module roots and delegate behavior to owning crates instead of becoming a second implementation layer.

## Crate layout

Keep `lib.rs` thin. It should declare modules and re-export deliberate public API, not contain implementation.

Put implementation in focused modules under `src/`. If a module is getting large or starts mixing unrelated concepts, split it before adding more behavior.

Default new items to crate-private visibility. Make items public only when they are part of a deliberate crate API or facade surface.

Crate README files are generated from `Cargo.toml` metadata. Do not edit them manually.

## Adding a Rust workspace crate

Add a crate only when it creates a clear ownership boundary. Before adding one, decide:

- which domain owns the crate and why existing crates should not own the code
- whether the crate is production, boundary, test-only, benchmark-only, facade, or support code
- which internal crates it may depend on without reversing architecture direction
- whether its API is public or `pub(crate)` implementation detail
- whether it must stay independent of Python, terminal rendering, async runtimes, or process globals

When adding the crate:

- add it to the workspace members in `Cargo.toml`
- add it to the Rust shard matrix in `.github/workflows/ci-tests-multiplatform.yml`
- give `package.description` the exact crate summary that should appear in generated README files
- keep `lib.rs` thin and put declarations in focused modules
- add the crate to `scripts/generate_internal_crate_graph_policy.py` with its classification and layer
- regenerate crate README files with `python scripts/generate_crate_readmes.py`
- regenerate the crate graph policy fixture with `python scripts/generate_internal_crate_graph_policy.py`
- run both generator checks before finishing
- run the Rust test script

## Moving behavior between crates

Move behavior when the current crate no longer owns the concept, when downstream crates need the same logic, or when the dependency direction would otherwise become inverted.

When moving code:

- move the tests or fixtures that define the invariant with the owning implementation when practical
- update facade re-exports deliberately rather than preserving accidental paths
- regenerate crate README and crate graph policy artifacts if crate metadata or dependencies changed
- run the Rust test script
